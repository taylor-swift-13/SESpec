\begin{abstract}
Automatically generating formal specifications including loop invariants, preconditions, and postconditions for legacy code is critical for program understanding, reuse, and verification. However, the inherent complexity of control and data structures in programs makes this task particularly challenging, especially when no verification goal is provided to drive synthesis. This paper presents \toolname, a framework that integrates symbolic execution with large language models (LLMs) and a formal verifier (Frama-C/WP) to synthesize verifier-checked C program specifications. For loop-free fragments fully covered by the symbolic executor, \toolname\ computes exact path-sensitive postconditions, composing the specifications of ordinary (non-recursive) callees along the way; at the remaining boundaries (loops, recursive data structures, and fragments outside the symbolic executor), it uses the available symbolic facts to guide LLM synthesis whose candidate specifications are then checked by the verifier. During symbolic execution, \toolname\ decomposes the synthesis task by pausing at program boundaries, where the symbolic state is injected into annotation templates and LLM prompts. When a specification is faulty, verifier feedback is combined with symbolic information to refine the failed candidate rather than re-sampling blindly. This design supports goal-independent specification generation, because it derives functional relations from symbolic states and verifier feedback rather than relying solely on externally provided assertions. Through extensive evaluation across numerical, pointer, struct, and linked-list benchmark families and an additional goal-independent benchmark (\textbf{\toolname-400}), \toolname\ outperforms the state-of-the-art LLM-based tools across diverse program classes, including the goal-independent setting in which no verification target is provided.
\end{abstract}

\section{Experiments}
\label{sec:experiments}

This section evaluates \toolname, our symbolic execution-based approach to automatic specification generation. The main experiments use benchmark families from prior invariant and specification generation work, which enables direct C/ACSL comparisons under established settings. Section~\ref{sec:large-scale-experiment} complements this evaluation with a separate goal-independent study, where assertions are removed and the generator must decide what functional behavior to specify.

\subsection{Experimental Setup}
\subsubsection*{Benchmark}
We evaluate our approach on benchmark families commonly used by recent specification and invariant generation tools. These include:  \textbf{SyGuS}~\cite{alur2019sygus}, collected by CODE2INV~\cite{Code2Inv_a_Deep_Learning_Framework_for_Program_Verification}; \textbf{OOPSLA}~\cite{Inductive_Invariant_Generation_via_Abductive_Inference}; \textbf{NLA}, collected by LIPuS~\cite{Loop_Invariant_Inference_through_SMT_Solving_Enhanced_Reinforcement_Learning}; the datasets from \textbf{SV-COMP} and \textbf{Frama-C}, collected by \autospec~\cite{autospec}.
In addition, we constructed three new benchmarks to capture more program scenarios: The \textbf{pIp} set consists of small C fragments adapted from a navigation component of an industrial control codebase, involving pointer and struct manipulations as well as branching structures. We use \textbf{pIp} as a small, self-contained industrial sample rather than as a claim about the complexity or scale of the original system. We carefully adapt and reformulate \textbf{pIp} programs into a format acceptable to Frama-C and QCP, thereby establishing a new dataset, which constitutes one of our contributions;
% The \textbf{struct-S} set is selected from a real-world Sun Search System in aerospace control softwares,  featuring pointer and struct manipulations alongside complex branches;
the \textbf{list-S} set is derived from the LIG-MM~\cite{LIG-MM} benchmark and includes all singly linked list programs from SLING and SV-COMP; and the \textbf{numer-S} set is a curated collection of additional programs, comprising 20 linear and 20 nonlinear loops, primarily drawn from CLAUSE2INV~\cite{DBLP:journals/pacmse/CaoWXYWCM25} and harder than those in \textbf{SyGuS} and \textbf{NLA}.

% For all benchmarks, we adapted them into a format acceptable to Frama-C while strictly preserving their original semantics.


\subsubsection*{Verifier}

All experiments are performed using Frama-C version 27.1 (Cobalt). We employ the WP plugin as the verification backend, which enforces a 10-second timeout per query, uses Z3 as the primary SMT solver, and applies the Typed memory model.  

\subsubsection*{Model}
Our LLM selection for evaluating specification generation balanced model maturity, prevalence, and cutting-edge performance:
\textbf{GPT-3.5-turbo} is an earlier, foundational model that serves as an essential baseline; \textbf{GPT-4o-mini}, a smaller, established model optimized for efficiency; \textbf{GPT-4o}, a widely adopted model for general code comprehension and generation and \textbf{Claude 3.7 Sonnet}, a stronger hybrid model with advanced reasoning and code understanding. For all experiments, we use a fixed sampling temperature of $0.7$ to balance output diversity and stability.

\section{Conclusion}
\label{sec:conclusion}

% We presented \toolname, an end-to-end framework for generating verifier-checked C program specifications by integrating symbolic execution, LLMs, and Frama-C/WP. Three design choices distinguish \toolname\ from prior LLM-based work: boundary-driven decomposition, symbolic-state-guided generation, and verifier-guided refinement (Section~\ref{sec:intro}). Together they keep each LLM call local and grounded in symbolic facts rather than free-form sampling.

% On the eight benchmark families used by the directly compared tools, \toolname\ reaches 100\% on \textbf{SyGuS}, 87\% on \textbf{OOPSLA}, 86.7\% on \textbf{NLA}, and 95.8\% on the linked-list \textbf{list-S} benchmark with Claude 3.7 Sonnet, outperforming AutoSpec and ACInv across the LLM-based comparison. On the goal-independent \textbf{SESpec-400} benchmark, the full pipeline lifts \emph{Valid} from 13.0\% (single-shot LLM) to 68.0\% on gpt-4o, 93.3\% on gpt-5.4-mini, and 93.0\% on gpt-5, and the pairwise judge ranks \toolname\ strictly stronger than the C/ACSL AutoSpec baseline on 50.0\% of both-valid pairs. The SpecGen strength result is reported as cross-ecosystem context rather than as a direct verifier-stack comparison.

% Future work should extend \toolname\ along three complementary axes. First, broader symbolic-execution coverage is needed for recursion, complex heap structures, external calls, and deeper interprocedural state. Second, stronger loop-invariant generation is needed for nested loops and cross-loop relations that are not fully exposed by the current boundary-local context. Third, verifier headroom remains a limiting factor: auxiliary-lemma synthesis, alternative WP memory models, and ITP integration are needed for inductive or heap-heavy obligations that current ATP backends do not discharge. Broader applicability therefore depends on both stronger generation and a wider verifier surface.


We presented \toolname, an end-to-end framework for generating verifier-checked C program specifications by grounding LLM synthesis in symbolic states and verifier feedback.

The experiments also expose the current boundary of this approach: as analyzed in Sections~\ref{sec:limitations} and~\ref{sec:threats}, the dominant residual failures are inductive, recursive, and heap-heavy proof obligations beyond the current Frama-C/WP backend, so further progress depends on a wider verification surface rather than on prompting alone.

Looking ahead, specification generation may become more agentic as reasoning models improve. Instead of following a fixed symbolic-execution-driven order, future systems could let an LLM agent decide when to invoke symbolic execution, strengthen specifications or introduce lemmas. The key principle should remain unchanged: every generated specification should be grounded in symbolic states and verifier feedback, rather than free-form generation.
